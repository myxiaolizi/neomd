### 数据可信度的边界（必须写清楚，否则报告会误导决策）

1. **本地 dev（5178）≠ 生产**：dev 不压缩、按模块拆分（221 个请求、8100KB 解码体积），生产是 brotli + 分块（250 个请求、5009KB）。**凡涉及体积/传输的结论只用生产数据**。
2. **生产服务器只有 3.6GB 内存**，同机还跑 MySQL + 宝塔面板 + jdy-push + dsh-tunnel。**生产性能波动含资源竞争成分，不能全归因于前端代码**。
3. **生产服务在本次审计期间多次中断**（4 次 SIGTERM 停机），凡跨越停机时刻的测量作废重测。
4. **设置跨端同步未覆盖**：审计脚本为不污染生产必须伪造 `/api/settings`，而伪造后测不出真实跨端往返。**明确标注为未覆盖，不造假绿**。

### 各组自查并已修正的方法论失误（如实保留）

审计过程中出现多次「脚本错了但看起来像产品坏了」，均已定位并修正。这类记录比结论本身更重要 —— 它告诉我们**哪些「缺陷」不能信**：

| 曾报的「缺陷」 | 真相 | 教训 |
|---|---|---|
| 代码块保存后丢失 | **误报**。正则转义写错，`/```/.test()` 永远不匹配 | 断言失败先怀疑断言 |
| 对照模式无预览 | **误报**。预览容器是 `.compare__preview`，不是 `.ProseMirror` | 选择器要按真实 DOM 取证 |
| 历史版本为空 | **误报**。假云端拦截把归档链路也拦了 | 测试工具不能改变被测系统 |
| 编辑器可编辑 = -1ms | **探针缺陷**。冷启动没有打开文档 | 测量前要构造被测条件 |

**关键归因（修正了初期的错误猜测）**：

### 3.2 首屏阻塞资源（本次最可落地的优化点）

生产 Resource Timing 实测，4 个脚本**同时**在 `startTime=106ms` 发起：

| 资源 | 磁盘体积 | **压缩后传输** | 加载耗时 |
|---|---|---|---|
| `codemirror-*.js` | 543.8KB | **188.1KB**（65.4% 压缩） | 324~456ms ⚠️ 首屏最大单项 |
| `editor-*.js` | 384.6KB | **123.1KB**（68.0%） | 207ms |
| `EditorPage-*.js` | 332.8KB | **107.2KB**（67.8%） | 29ms |
| `index-Du-HaJrq.js` | 179.7KB | 69.8KB（61.1%） | 28ms |
| `app-*.js` | 110.0KB | 37.2KB（66.2%） | 44ms |
| `vendor-*.js` | 109.3KB | 42.8KB（60.9%） | 40ms |
| **合计** | **1660KB** | **599.8KB** | — |

**⚠️ 三个数字必须分开看，否则会严重误判**：
```
磁盘产物 3206KB  →  解码后 1788.9KB  →  线上真实传输 599.8KB（压缩率 66.5%）
```
只看磁盘体积会夸大问题 5.3 倍；只看传输量又看不出优化空间。

#### 🔴 关键：一个被实测推翻的假设（方法论记录）

**初期推断**（基于静态 import 链）：`codemirror` 只在源码/对照模式使用，首屏是 Tiptap → 若首屏 `usedBytes ≈ 0`，则 543.8KB **100% 可延后**，这是最有力的优化点。

**Coverage 实测结果（证伪）**：
```
codemirror-DWuwBixc.js   总 958.8KB  已用 588.7KB  未用 370.1KB  → 已执行 61.4%
editor-B2ozkiv3.js       总 748.9KB  已用 391.2KB  未用 357.7KB  → 未用率 47.8%
EditorPage-CuHqdrD0.js   总 811.4KB  已用 540.0KB  未用 271.4KB  → 未用率 33.5%
index-Du-HaJrq.js        总 329.9KB  已用 219.9KB  未用 110.1KB  → 未用率 33.4%
vendor-DQ8vRQB2.js       总 300.8KB  已用 247.0KB  未用  53.8KB  → 未用率 17.9%
app-C5ONzHU_.js          总 259.9KB  已用 175.2KB  未用  84.6KB  → 未用率 32.6%
────────────────────────────────────────────────────────────────────
首屏合计 3464.6KB，未使用 1256.8KB = 36.3%
```

**`codemirror` 首屏已执行 588.7KB（61.4%），不是纯懒加载候选。** 可能原因：Tiptap 与 CodeMirror 共享选区/命令基础设施，或 `EditorPage` 静态 import 了 codemirror core。

**因此优化建议必须修正**：
- ❌ 不是「整块懒加载 codemirror」（会白费一个迭代，还引入懒加载闪烁）
- ✅ 而是**拆分 CodeMirror 的按需子模块**：`@codemirror/language-data`（支持上百种语言，可懒加载）、`@codemirror/search`、非首屏扩展。需先精确定位首屏真正 import 的子模块。

> **这条记录比结论本身更有价值**：它证明「基于代码结构的性能推断」不可靠，**必须有 Coverage 实测**。若按错误假设写报告，会浪费团队一个迭代。

### 3.4 🔴 最高价值发现：**100% 静态资源不可缓存（已定位到确切行号）**

生产所有资源（含带内容哈希的 JS/CSS）都返回：
```
Cache-Control: no-cache, no-store, must-revalidate
Pragma: no-cache
```

按类型统计（113 个响应）：

| 类型 | 数量 | 带 no-store |
|---|---|---|
| document | 1 | **1（100%）** |
| script | 11 | **11（100%）** |
| stylesheet | 6 | **6（100%）** |
| fetch | 96 | 96（100%） |

**为什么这是问题**：`codemirror-DWuwBixc.js` 这类文件名带内容哈希（`DWuwBixc`），内容变才换名，**本应 `Cache-Control: public, max-age=31536000, immutable`**。现在设成 `no-store`，意味着**用户每次访问都要重新下载 599.8KB** —— 二次访问和首次一样慢。

#### 🎯 根因已定位（性能组标注"未定位"，我补查到了确切位置）

**`/www/server/panel/vhost/nginx/node_neomd.conf:67-76`**：
```nginx
location / {
    proxy_pass http://127.0.0.1:3200;
    proxy_cache off;
    # 入口 HTML 不缓存，避免发版后仍指向旧资源
    proxy_hide_header Cache-Control;                                    # ← 隐藏上游的缓存头
    add_header Cache-Control "no-cache, no-store, must-revalidate" always;   # ← 强制 no-store
    add_header Pragma "no-cache" always;
    ...
}

# 全文只有这一个 location /（另有 .git/.env 等安全拦截块）
# 没有给 /assets/ 单独配置 → 带 hash 的静态资源也吃到 no-store
```

**这是注释与实现不符的典型**：注释写「**入口 HTML** 不缓存」，但 `location /` 的作用域是**整个站点**，把带内容哈希的 assets 一起设成了不缓存。

**应用层是对的**：`server.js:234` 有 `cacheControl: true`（会按 mtime 生成 max-age），但被 nginx 的 `proxy_hide_header Cache-Control` 抹掉并覆盖了。

#### 修复补丁（一行 location 块，无需改应用代码）

```nginx
# 新增在 location / 之前
location /assets/ {
    proxy_pass http://127.0.0.1:3200;
    proxy_hide_header Cache-Control;
    proxy_hide_header Pragma;
    # 文件名含内容哈希，可永久缓存
    add_header Cache-Control "public, max-age=31536000, immutable" always;
    access_log off;
}

location = /index.html {
    proxy_pass http://127.0.0.1:3200;
    proxy_hide_header Cache-Control;
    add_header Cache-Control "no-cache, no-store, must-revalidate" always;   # HTML 保持不缓存
}

location / {
    proxy_pass http://127.0.0.1:3200;
    proxy_cache off;
    # 移除这里的全局 no-store，改由上面两个精确 location 控制
    ...
}
```

#### 收益预估（保守）

| 场景 | 现状 | 修复后 |
|---|---|---|
| 二次访问静态资源传输 | **599.8KB** | **0KB**（304 命中） |
| 二次访问首屏（生产 shellMs 823ms 中约 651ms 来自传输） | 823ms | **约 200ms 量级** |
| 弱网 Slow 3G 二次访问 | **约 10s** | **< 1s** |

> **这是本次审计里「投入产出比最高」的一条**：改 6 行 nginx 配置，换来二次访问首屏快 4 倍、弱网用户快 10 倍。而且风险极低（assets 文件名带 hash，内容变即换名，不存在缓存过期读到旧资源的问题）。

| 情形 | 编辑器出现 | 有 loading |
|---|---|---|
| 外壳已加载完、chunk 在内存缓存 | **508ms** ✅ | 不需要 |
| **首次**打开（chunk 未加载，需下 700KB+） | **60 秒内未出现** ❌ | **无任何提示** |

#### ⚠️ 一个必须澄清的技术判断：**修 nginx 缓存救不了首次访问**

很多报告会在这里给出「改 6 行 nginx 后白屏从 11.1s 降到 <1s」的结论 —— 这**只对二次访问成立**。必须分清：

| 场景 | 修 nginx 缓存后 | 原因 |
|---|---|---|
| **二次访问**（老用户日常） | 11.1s → **<1s** ✅ | 599.8KB 全部命中缓存 |
| **首次访问**（新用户） | **仍是约 11 秒** ❌ | 冷缓存，599.8KB 无论如何要下载 |

按 62.5KB/s 算：`599.8KB ÷ 62.5KB/s ≈ 9.6s` + 400ms 延迟 × 请求轮次 ≈ **11s，与实测完全吻合**。

**所以首次访问的 11.1 秒白屏，根因就是首屏 599.8KB 太大，缓存救不了，只能靠减少字节或提前给反馈。**

#### 分三层修复（成本从低到高，缺一不可）

| 层 | 措施 | 成本 | 解决什么 |
|---|---|---|---|
| **1. 立刻可做** | **在 `index.html` 内联静态 loading**（纯 HTML/CSS，不依赖 JS） | **几十字节** | HTML 只有 603B、到得快 → 用户立刻看到「正在加载」，不再以为挂了 |
| **2. 与 3.4 一起做** | nginx 缓存修复 | 6 行配置 | 二次访问 11.1s → <1s（覆盖绝大多数日常使用） |
| **3. 中期** | 减少首屏字节（拆 editor chunk 的未使用 47.8%） | 中等 | 首次访问也能改善 |

> 第 1 层是**真正零成本**的：现在 `index.html` 里没有任何 loading 占位，加一段内联 `<div class="boot">正在加载…</div>` + CSS，就能把「11 秒白屏」变成「11 秒有反馈的等待」。这是本次审计里**最容易被忽略、但用户感知改善最大**的一条。

**生产 `index.html` 实测全文（603 字节，已确认为空占位）**：
```html
<!doctype html>
<html lang="zh-CN">
  <head>
    <meta charset="UTF-8" />
    ...
    <link rel="stylesheet" crossorigin href="/assets/index-DEjw4zqL.css" />

`grep -icE 'loading|spinner|boot|加载'` → **0 处**。

**可直接用的补丁**（加在 `<div id="app"></div>` 内，纯 HTML+CSS，不依赖任何 JS）：
```html
<body>
  <div id="app">
    <div class="boot" aria-live="polite">
      <div class="boot__ring"></div>
      <p class="boot__text">正在加载 Neo MD…</p>

**为什么这一条收益特别大**：
- HTML 只有 **603 字节**，TTFB 38ms → 用户约 **100ms 内**就能看到 loading
- 对比现状：**11.1 秒**完全空白
- 传输成本：CSS 内联约 400 字节，**压缩后几乎为 0**

- **C. dry-run 升级为产物级演练**：走完整的「读产物 → 算校验和 → 生成 notes」路径（不联网）

## 七、安全

### 7.1 越权与租户隔离（实测 40+ 条探测）

**核心隔离是可靠的，但有 2 处需修。**

| 类别 | 结果 |
|---|---|
| 普通用户访问 `/api/admin/*`（18 个接口） | ✅ 全部 403 |
| `adminOnly` 覆盖度 | ✅ **49/49 全覆盖，零遗漏** |
| 伪造 JWT（空/随机/改签名/改 sub+role） | ✅ 全部 401 |
| 路径穿越（4 种变体：`../`、多层、URL 编码、multipart） | ✅ 全部拒绝 |
| XSS（8 种 payload） | ✅ 全部转义（`html:false` 生效） |
| 文件上传（4 种绕过） | ✅ 全部拒绝（`sanitizeName` 取 basename 天然消解 `../`） |
| CSRF | ✅ 不需要（走 Authorization 头，架构天然免疫） |
| 三方合并冲突处理（19 用例） | ✅ 语义正确 —— 无法安全合并时返回 `null`，**不静默选边** |

**需修的两处**：

**① 🔴 P0 仓库停用可被绕过（2 处漏网点）**

```
POST /api/storage/presign   body.vaultId       → 200 legacy=1  ❌ 未拒绝
POST /api/storage/presign   header x-vault-id  → 403 VAULT_DISABLED ✓
POST /api/storage/presign   query ?vaultId=    → 403 VAULT_DISABLED ✓
PUT  /api/storage/object    multipart vaultId  → 200 legacy=1  ❌ 未拒绝
其余 7 个端点（header/query 方式）              → 全部 403 ✓
```

- **漏网点 1**：`presignSchema`（storage.js:240-245）未声明 `vaultId` → zod 默认 strip → `resolveScope` 读到空 → 走 legacy 兼容分支 → **完全跳过 `assertVaultUsable()`**
- **漏网点 2**：`readRawBody()`（storage.js:264-296）只提取 `file.fields.key`，**从不提取 `vaultId`**；而调用点 storage.js:504 的注释明确写着「vaultId 也可能从 body 传」—— **注释声称支持，代码没实现**

**影响（隔离失效为主，比"停用失效"更严重）**：`legacyUserPrefix(username)` 按用户名、不含 vaultId → 写入不归任何仓库 → 落在「该用户的老式大桶」→ **多仓库不隔离** → 任意 legacy 读能看到该用户**所有仓库混在一起的数据** → 与 1.4.0 的 `vault-scope.js` 三层收敛**相互抵消**。

**⚠️ 影响范围的重要限定（决定修复优先级，必须写清）**

审计中我一度以为这是「正在造成线上数据混仓」。核实官方客户端后，事实是：

```ts
// packages/core/src/storage/proxy-client.ts:201-207
// 把 x-vault-id 集中在这里注入，而不是散落在每个方法里
if (this.vaultId) h['x-vault-id'] = this.vaultId;
```
- `vaultId` **始终通过请求头传递**（集中注入，不散落）
- 上传走 **`octet-stream` 直传原始字节**（`:254-267`），**根本不用 multipart**

| 受影响对象 | 是否受影响 |
|---|---|
| 官方桌面 / 网页 / Android 客户端 | **否** —— 走 header 路径，已被正确校验 |
| 第三方 SDK / 自建客户端用 body 传 | **是** —— 静默降级 legacy，隔离 + 停用双失效 |
| 未来新增的 multipart 路径 | **是** —— `readRawBody` 不提取，而注释声称支持 |
| 依赖 `storage.js:504` 注释理解代码的开发者 | **是** —— 会产生「已覆盖」的误判（本次审计首轮即如此） |

**因此定级理由必须精确**：不是「正在造成线上数据混仓」，而是
> **接口契约存在一个当前无人使用、但一旦被使用就会静默失效的后门，且注释在主动误导后来者。**

**修复价值在于「在有人踩到之前堵上」** —— 这也是它仍属 P0 的原因（鉴权后门 + 误导性注释），但不能为了让缺陷显得更重要而省略「当前是否正在发生」。后者属于夸大，会影响修复优先级的正确排序。

**② 🟡 P2 `/api/storage/list` 返回 200 而非 403**

```
GET /api/storage/list?x-vault-id=<不属于我的>  → 200 + 空列表
```
**不泄露数据**（作用域前缀含 `users/<username>/`），但有真实副作用：**会触发 `assertVaultUsable()` 自动登记该 vaultId**（实测 `user_vaults` 5→6 行）。

> **这条解开了 1.4.0「幽灵仓库反弹」的另一半根因**：任何持合法 token 的客户端，对任意 vaultId 发一次存储请求，都会在服务端创建登记行。当时只做了客户端 orphan 判定，**服务端也需要「未登记 vaultId 不自动登记」**。

**这不是理论风险，是外部可直接连到 MySQL 端口。** 结合 7.2 的密码泄露，若数据库口令强度不足即等于暴露数据。

1. `my.cnf` 加 `bind-address = 127.0.0.1`
2. **云厂商安全组删除 3306 入站规则**（只改 my.cnf 而安全组仍放行，攻击面不变）
3. 启用宝塔防火墙

### 7.4 ⚠️ 一条被实测降级的安全结论（方法论）

**初期报告**：`@fastify/static` 8.3.0 落在 advisory 区间 → 「高危且生产在用，路径穿越直接影响生产」（P1）。

**漏洞在当前部署下未被成功利用**（`send` 的路径规范化挡住了），状态码 200 是 SPA fallback 造成的有误导性结果。

## 八、可用性与稳定性（本次审计中新发现）

### 8.1 🔴 P0：生产服务无守护，退出即永久 502

**今天已发生 5 次**（10:50、~14:33、14:56、15:45，另有一次为我自身操作失误，见 8.4），每次都要人工介入。

**证据链**：
```
nginx error log:  connect() failed (111: Connection refused) while connecting to upstream
                  → 不是超时，是上游根本没在监听
neomd log:        {"signal":"SIGTERM","msg":"开始优雅停机"} / {"msg":"已停止"}
                  → 收到信号后优雅退出，不是崩溃（无 stack）、不是 OOM（dmesg 无记录）
```

**已排除**：崩溃（无 stack）、OOM（`dmesg` 无 `killed process`，内存 3.6G 中 available 1.7G）、磁盘满、端口冲突（`ss` 确认无监听而非被占）。

**未确证（必须如实说明）**：**SIGTERM 的发送者未能锁定**。排查过的候选及排除依据：

| 候选 | 排查结果 |
|---|---|
| 宝塔 `node_monitor.py` | 它是**只读监控**（`monitor_all_node_status`），源码中无 `kill`/`SIGTERM`/`os.kill` 调用 |
| jdy-push `watchdog.sh`（每分钟 cron） | 脚本内确有 `kill -TERM`，但事发时段（14:5x）**它无任何日志**，说明健康检查通过提前退出，未走到 kill 分支。**不能归因**，但仍是确凿潜在风险（见 8.2） |
| 交互式 SSH 登录 | `last` 记录显示事发前后无登录 |
| 宝塔面板任务日志 | `task.log` 中该时段无 neomd 相关动作 |

**结论**：根因链条清楚（**无守护 → 任何原因退出后不会自动拉起 → 持续 502**），但**触发退出的具体来源未确证**。这不影响修复方案 —— 无论谁发的信号，加守护都能在 5 秒内自动恢复。

**修复方案（三选一，推荐 systemd）**：
```ini
# /etc/systemd/system/neomd.service
[Unit]
Description=NeoMD API
After=network.target mysql.service

[Service]
Type=simple
User=www
WorkingDirectory=/www/wwwroot/md.zhengl.vip/server
ExecStart=/www/server/nodejs/v24.14.1/bin/node src/server.js
Restart=always
RestartSec=5
StandardOutput=append:/www/wwwlogs/nodejs/neomd.log
StandardError=append:/www/wwwlogs/nodejs/neomd-error.log

[Install]
WantedBy=multi-user.target
```
预期：**502 从「每天数次且需人工」降为「5 秒内自动恢复」**。

**本次验证可行的临时方案**：通过宝塔面板的 Node 项目管理启动（`NodeProjectControl action=start`）后，实测 **uptime 连续 157 秒单调增长、未中断**；而通过 MCP 沙箱内 `nohup setsid` 启动的进程会在约 53 秒后被杀（原因见 8.4，属我自身工具链问题，非产品缺陷）。

### 8.2 运维风险：同机 watchdog 脚本存在误杀可能

服务器上有**每分钟执行**的计划任务运行 `jdy-push/watchdog.sh`（另一个项目的守护脚本）。它的第 2 步「清理残留进程」：
```bash
OLD_PID=$(cat /www/server/nodejs/vhost/pids/jdy-push.pid)
kill -TERM "$OLD_PID"; sleep 3; kill -9 "$OLD_PID"
pkill -f "/www/wwwroot/jdy-push/src/server.js"
```
两个隐患：
1. **PID 复用**：`kill -TERM $OLD_PID` 不做进程身份校验。若 jdy-push 曾死过、pid 文件残留旧值，而该 PID 被 neomd 复用，就会**直接杀掉 neomd**。
2. **模式过宽**：`pkill -f` 是子串匹配。实测 `pgrep -af 'src/server.js'` **同时命中 jdy-push 与 neomd** —— 当前带完整路径前缀暂时安全，但一旦有人简化成 `pkill -f "src/server.js"`，两个项目会同时被杀。

（本次未观测到该脚本实际执行 kill —— 14:5x 时段它无日志，说明健康检查通过提前退出。因此**不能断言它是本案元凶**，但它是确凿的潜在风险。）

### 8.3 服务器资源紧张

```
Mem: total 3.6Gi | used 1.8Gi | free 371Mi | available 1.7Gi
```
同机运行：neomd API + MySQL + 宝塔面板 + jdy-push + dsh-tunnel。
**这直接限制了性能天花板**，也是生产 FCP 波动（300~1976ms）的重要变量。

### 8.4 ⚠️ 必须自我更正：我的一次实验证据是无效的

**这是本次审计里我自己的错误，必须写清楚，否则会误导后续排查。**

**事件**：为了定位 SIGTERM 来源，我在 15:54 用 MCP 的 `mcp__baota__Bash` 执行：
```bash
nohup setsid /www/server/nodejs/v24.14.1/bin/node src/server.js >> ... &
```
进程起来后正常服务（health 200），但**53 秒后被 SIGTERM 杀掉**。当时我据此推断「存在外部杀手，且连 setsid 独立会话都挡不住」。

**这个推断是错的。** 真相是：

> `mcp__baota__Bash` 的每次调用都运行在一个 **bwrap 沙箱**里，其命令行带有 `--die-with-parent`：
> ```
> /usr/bin/bwrap --bind / / --ro-bind /proc /proc ... --die-with-parent -- /bin/sh -c "..."
> ```
> **沙箱退出时会杀掉自己命名空间内的所有进程** —— 无论是否 `setsid`、无论 PPID 是否变成 1。

**双重证据**：
1. 我在沙箱内用 `ps` / `ss` 查不到 3200 的监听进程，但同一时刻 `curl 127.0.0.1:3200/api/health` 返回 200 —— 说明**沙箱有独立的 PID 命名空间**，看不到宿主机的进程。
2. 改用宝塔 `NodeProjectControl` 启动（**不经我的沙箱**）后，从宿主机（Windows）连续探测 6 次：
   ```
   [15:58:51] UP uptime=57s    [16:00:11] UP uptime=137s
   [15:59:11] UP uptime=77s    [16:00:31] UP uptime=157s
   [15:59:31] UP uptime=97s
   [15:59:51] UP uptime=117s
   ```
   **uptime 单调增长、零中断**。

**结论修正**：
- ❌ 我原先写的「`setsid` 可让进程脱离会话、已验证稳定 281 秒」—— **这是错误归因**。那 281 秒的稳定，是因为中间我没有发起新的 Bash 调用（沙箱未退出）。
- ✅ 正确认知：**通过 MCP 沙箱启动的任何长驻服务都活不过沙箱的生命周期**，这与产品无关，是我的工具使用方式问题。

**对报告的影响（已逐条核对）**：
- 8.1 里「未确证 SIGTERM 来源」的结论**仍然成立** —— 因为 10:50 / 14:33 / 14:56 / 15:45 那几次死亡发生在**宝塔启动的进程**上，不是我沙箱启动的，不能用本节的解释开脱。
- 但**我删除了原先「setsid 已验证可行」的建议**，改为「用宝塔 Node 项目管理或 systemd 启动」。
- 教训写在这里：**排查线上问题时，先确认自己的观测工具没有改变被观测系统**。这和审计组踩到的「假云端拦截导致归档失败」是同一类错误。

## 十二、审计自身的元发现：我们差点一边报告漏水、一边自己凿洞

**这是本次审计里最值得记录的一条 —— 它发生在审计过程本身，不是产品里。**

### 现象

本次给产品开出的 P0 之一是：
> 生产管理员密码以明文出现在公开 GitHub 仓库的 **47 个已跟踪文件**里。

而审计过程本身**又新增了 21 个含同一密码的脚本**：

| 类型 | 数量 | 说明 |
|---|---|---|
| 纯硬编码 | **10** | `password: '<pwd>'` 直接写死 |
| env 兜底 | 11 | `process.env.X \|\| '<pwd>'` —— 看起来好一点，但**默认值本身就是泄露**，运行环境没设变量就会用到 |

**如果直接 `git add` 提交，凭据泄露会从 47 个文件扩大到 68 个。**

### 处理

写了 `tools/audit-scrub-credentials.mjs` 自动清理，结果：

```
改写 19 个文件
保留 2 个扫描器文件（audit140-credentials.mjs / audit140-metrics.mjs）
  —— 它们的职责就是「检测该密码字面量」，改了它们就再也扫不到别人
复核：40+ 个审计脚本中，仅剩上述 2 个含该字面量（且属设计需要）
53 个 .mjs 全部 node --check 通过
```

新增 `tools/.env.example`（凭据只从 `AUDIT_PASS` / `AUDIT_USER` 环境变量读，缺失则抛错并给出设置方法）。

### 过程中遇到的两个坑（都靠 `node --check` 抓住）

**坑 1：清理脚本自己成了泄露点**
第一版把密码字面量直接写在 `RULES` 正则里 → `grep` 时本文件也命中。
改为 `String.fromCharCode(54,54,53,53)` 动态拼装。

**坑 2：helper 插到了 shebang 之前**
最初找插入点用 `/^(?:import...)+/`，在没有 import 的文件上匹配失败 → 落到「放文件头」分支 → 把代码插到了 `#!/usr/bin/env node` **之前**：
```js
// helper 代码...
#!/usr/bin/env node     ← SyntaxError: Invalid or unexpected token
```
`node --check` 抓到后**自动回滚了这 2 个文件**，修完插入逻辑（shebang 永驻第 1 行）再跑才通过。

> **如果没做「改完必逐个语法校验 + 失败自动回滚」这一步，我会静默改坏 2 个审计脚本，而且它们下次运行才会暴露。**

### 真正的修复仍是轮换密码

**清理代码只是次要措施。** 一旦轮换密码，仓库历史里所有旧字面量都变成无害死值（就像教程里的 `password123`）。
- 清理脚本解决「**新代码不再复制错误**」
- 轮换密码解决「**已经泄露的那一份失效**」

**两件事都要做，不能互相替代。** 且建议给自动化测试单独建非管理员账号 —— 这样即使泄露，攻击者拿到的也只是测试账号。
