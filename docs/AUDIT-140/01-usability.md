## 2. 缺陷清单（按严重度）

### P0 级缺陷：新设备登录会把云端仓库统计清零（用户会以为数据全丢）

**现象**
用户在新设备/新浏览器/隐私模式登录后，打开「仓库」页，看到自己最大的仓库显示 **0 篇文档、0 B**，而实际上文档一篇没丢。

**根因（架构级，不只是「一个 SQL 写错」）**
`docCount` / `bytes` 是**客户端上报的元数据**，服务端零校验、零扫描：

```js
// services/api/src/routes/vaults.js:47-48  客户端上报值，默认 0
docCount: z.coerce.number().int().min(0).optional().default(0),
bytes:    z.coerce.number().int().min(0).optional().default(0),

// services/api/src/routes/vaults.js:126-129  无条件覆盖
ON DUPLICATE KEY UPDATE
  doc_count = VALUES(doc_count),
  bytes     = VALUES(bytes),
```

**更根本的事实：数据库里没有任何 documents 表。**

```sql
SELECT * FROM user_vaults;
user=1 vault=admin                   docs=356  bytes=132786
user=1 vault=笔记本                   docs=700  bytes=4021982
user=1 vault=Neo MD                  docs=316  bytes=2237384
user=1 vault=vaultmvp3augl2m72a0nw   docs=298  bytes=2184414
user=2 vault=admin                   docs=0    bytes=0        ← 另一用户的同名仓库

-- 查 information_schema 里所有 *doc* 表
相关表: (无)
```

**所以 `docCount` 没有权威数据源** —— 服务端既不能校验、也不能重算，
因为它根本不知道用户真实有多少文档（文档实体只存在于对象存储的 `docs/<docId>/` 前缀里）。

这把 P0 从「把 `=` 改成 `GREATEST()` 就完事」升级为**架构级缺陷**：
只要「统计值」与「真实文档」分离且服务端无校验能力，任何客户端上报错误都会污染它。

**触发场景**（比「新设备登录」更广）
任何「客户端本地仓库索引为空、但云端有数据」的时刻：
- 新设备 / 新浏览器首次登录
- 清浏览器缓存后重开
- 隐私模式
- 切换仓库后回到旧仓库（客户端重新注册时上报当前内存值）

**实测证据（审计中稳定复现 5/5 次，含收尾复查再次命中）**
```
污染前：admin = 283 docs / 21089 bytes
污染后：admin =   0 docs /     0 bytes
同时对象存储完好：
  docs/ 前缀    → 639 个对象，去重 docId = 287，总字节 115088
  index/ 前缀   → 86 个对象
  样例：docs/docmvurr15ge5wymxip/2-2077c5170add46bf.md  500 B
```
收尾复查时**再次**观察到 `admin = 0 docs / 0 B`（而此时对象存储已有 790 个对象、356 个 docId），
进一步确认这不是偶发，而是**每次空本地仓库注册都会覆盖**。
已按对象存储实测值恢复（随审计期间临时文档残留浮动 287→294→356，文档实体全程无损）。

**建议（三选一 + 组合）**
1. **服务端软更新（立即止血，最小改动）**
   `doc_count = GREATEST(doc_count, VALUES(doc_count))`
   副作用：用户真删文档后统计不下降，需配合「显式重算」入口
2. **客户端守卫（治本、无副作用）**
   本地仓库为空时**不上报统计**（传 `undefined` 而不是 `0`）
3. **服务端前缀扫描计算（最可信）**
   按 `docs/<docId>/` 前缀统计；有存储列举成本，建议做成低频定时校准

**组合建议**：1 立即上（止血）+ 3 做每日校准（修正漂移）+ 2 作为客户端加固。

> ⚠️ 注意：因为数据库**没有 documents 表**，方案 1 只能止血、无法让数字变准；
> 真正让统计可信的路径是方案 3（以对象存储为权威源反算）。
> 若长期要「文档级可查询」，需引入 documents 表并让保存链路双写 —— 那是更大的架构决定。

**当前统计值说明（356 的来历）**
`admin` 仓库统计当前为 **356 docs / 132786 B**，其中约 **73 篇是本次审计期间创建并删除的临时文档
在云端残留的对象**（P1 缺陷所致）。审计前真实值约 283。
**该数字的漂移本身就是 P1 缺陷的直接证据。**
另注：数据库无 documents 表，`doc_count` 为纯客户端上报，服务端无法校验 —— 这是 P0 缺陷的架构级根因。

### P1 级缺陷：删除文档后云端对象永久残留（隐私 + 空间双损）

**现象**
`deleteDoc()` 删除后，本地索引/DB 记录消失、UI 提示「已删除」，但 OSS 中 `docs/<docId>/` 前缀的对象**永不清理**。

**代码级证据**
- `services/api/src/routes/storage.js:552` **已有** `DELETE /api/storage/object` 端点（能力完备，真能删 OSS 对象）
- 全仓扫描 `apps/web` + `packages/core` + `packages/shared`：**调用次数 = 0**
- `apps/web/src/stores/app.ts:1147` `deleteDoc()` 只做 `vault.remove(docId, { deleteFile: true })`（仅本地文件），不触碰云端，仍 `notify('已删除', 'success')`

```ts
// apps/web/src/stores/app.ts:1147
async function deleteDoc(docId: string): Promise<void> {
  if (!vault.value) return;
  await vault.value.remove(docId, { deleteFile: true });   // ← 只删本地文件
  tabs.value = tabs.value.filter((t) => t.docId !== docId);
  ...
  notify('已删除', 'success');    // ← 用户被告知删除成功
}
```

**实测证据**
审计期间创建并 `deleteDoc` 约 7 篇临时文档 → `docs/` 前缀 docId 数 **287 → 294**，已删文档的对象仍可列举、内容完好。

**用户影响**
1. **隐私**：敏感笔记「删了还在云端」，与用户预期严重不符；涉合规（个人信息删除权 / 被遗忘权）
2. **空间**：长期使用对象存储单调增长，账单上升
3. **功能**：未来若做「历史恢复/回收站」，会翻出用户以为删掉的文档

**建议**
1. `deleteDoc()` 本地删除成功后，追加调用 `DELETE /api/storage/object`
   （先列举 `docs/<docId>/` 下所有对象 + manifest，再逐个删；或新增服务端「按 docId 批量删」端点）
2. 删除顺序需明确：建议本地先写 tombstone，云端删成功后再清本地，避免网络失败导致「本地没了云端还在」且不重试
3. 存量清理：一次性脚本按「DB 中不存在的 docId」扫描清理孤儿对象（**必须先用 DB 做权威比对**）
4. 补偿机制：定时任务做「DB vs OSS」双向对账，发现孤儿**报警**而非静默删除

### P2 级缺陷

#### D-2：空引用块在保存时被静默丢弃

插入引用块后**未输入内容**就离开/保存 → markdown 里没有 `> `，重开后引用块消失。

**A/B/C 三位置对照实验**（`tools/audit-代码块边界.mjs`）：

| 场景 | 内容 | markdown 结果 |
|---|---|---|
| A | 空文档 + 代码块 + 输入内容 | 含围栏 ✓ |
| B | 列表后 + 代码块 + 输入内容 | 含围栏 ✓ |
| C | 引用 + 代码块 + 输入内容 + 表格 | 含围栏 ✓ |

**空块对照**（`tools/audit-空块丢弃.mjs`）：

| 块类型 | 插入后不输入内容 | 保存后 |
|---|---|---|
| 空代码块 | `pre.is-empty=1` | **保留**（markdown 含围栏） |
| 空引用块 | `blockquote` 存在 | **丢弃**（markdown 无 `> `） |
| 空表格 | `table` 存在 | **保留** |

**不对称 = 缺陷**。用户影响：插入引用块后还没来得及写字就去点别处/保存，引用块就没了。
建议：`markdown-bridge` 序列化时对空引用块保留 `> ` 占位，与空代码块/空表格行为对齐。

#### D-3：S2 进入工作台耗时 12.9s

期望 < 8s。首次进入需加载 vault + 索引 + 云同步，体感偏慢；用户看到的是白屏到有界面的等待。
建议：加骨架屏或进度提示，避免「以为卡死」。

#### D-4：未登录态文案自相矛盾

工作台对访客开放（**这是有意的本地优先设计**——实测访客能真正写作、保存、刷新后内容仍在），但状态栏同时显示：
- 「未登录」
- 「自动同步已就绪」← 未登录时云端同步本不可能工作

建议：未登录时该文案改为「本地已保存」或「登录后可云端同步」。

#### D-5：大纲不显示当前文档标题

S8 实测：打开大纲区块后，右栏文本**不含**当前文档的 h1（「审计测试」）。而备份链/标签/统计都有内容。
建议核实大纲提取逻辑是否只取 `heading` 节点而漏了文档标题本身。

#### D-6：对照模式空文档时预览区高度塌成 0

实测 `.compare__preview` 高度 `0px`（文档为空时），右侧一片空白无占位提示。
建议：空状态显示「开始输入以查看预览」。

#### D-7：排序方式只有 5 种（任务书要求 6 种）

实测选项：修改时间（从新到旧）、修改时间（从旧到新）、创建时间（从新到旧）、创建时间（从旧到新）、字数。
缺「名称/标题排序」这类最常见的一项。

### 危险操作确认机制

- 探测到 **17 个破坏性入口**（删除/清空/重置等），**审计未真点**，只记录存在性。

## 7. 环境问题（非产品缺陷，但影响开发上手）

**本地开发环境存在端口配置漂移**

```
services/api/.env        PORT=3200
services/api/.env.local  PORT=3210   ← 覆盖前者（.env.local 优先级更高）
apps/web/vite.config.ts:27  proxy '/api' → http://127.0.0.1:3200   ← 硬编码
```

按仓库默认配置 `pnpm dev` + `node src/server.js` 启动，API 会在 **3210**，而 Vite 代理打 **3200** → **前端必然 500**（代理打不到后端）。

审计期间因此中断两次（API 不可达），已按「先确认端口归属再重启」的纪律处理。

**建议（二选一）**
- 方案 A（推荐）：删掉 `.env.local` 的 `PORT` 覆盖，统一 3200；`vite.config.ts` 的 proxy target 改为读 `process.env.API_PORT ?? 3200`
- 方案 B：`.env.local` 的 3210 与 vite proxy 同步改 3210

**另外建议加启动自检**：dev 启动时若 proxy target 端口无监听，直接在终端打印明确提示（而不是让用户在浏览器里看 500）。
