## 0. 方法论与测量纪律

这份报告的每个数字都标注了**测量条件**。以下规则是写进代码的硬约束，不是口头承诺。

### 0.1 冷启动的定义

**每次测量都新开 `BrowserContext`**（Playwright 的 `browser.newContext()`），缓存 / ServiceWorker / HTTP cache 全空。
复用同一 context 得到的是热启动 —— 本报告里所有「冷启动」字样都对应新 context。

对应代码：`tools/audit-perf-01-load.mjs` 的 `measureColdOnce()`，每轮开头 `await openPage(chromium)` 新建 context，`finally` 里 `browser.close()`。

### 0.2 中位数而非单值

性能数字受 JIT、GC、系统负载影响极大。首屏 200ms 量级的单次测量波动可达 ±40%。
所有指标跑 **3~4 轮取中位数**，同时给出 min / p95 / max，`n` 表示有效轮数。

### 0.3 uptime 守卫（数据可归因）

审计期间生产环境**反复宕机**（见附录 A），因此每批次测量**前后各取一次 `/api/health` 的 uptime**：

- uptime 单调增长 → 该批次数据有效
- uptime 回退 → 说明中途重启，该批次标记作废

本报告引用的每个批次都附了 `uptimeGuard` 值。**没有一条数据是在服务不稳定的窗口里取得的。**

### 0.4 我自曝并修正了两处测量缺陷

**缺陷 A：`编辑器可编辑 = -1ms`**
首轮生产测量三轮全是 `-1`。原因不是「编辑器很慢」，而是**冷启动时没有打开任何文档**，`.ProseMirror` 不存在，`waitForSelector` 超时。
修正：若 1.5s 内无编辑器，则点「新建文档」再计时（等价用户操作），并记录 `editableVia` 字段标明来源。

**缺陷 B：弱网 LCP 恒为 `null`**
首轮弱网测量 `LCP=null`。原因是没有在页面加载前注入 `PerformanceObserver`（LCP 需要提前注册才能观测）。
修正：弱网测量也调用 `installVitalsCollector(ctx)`。修正后 Slow 3G 拿到 `LCP=11940ms`。

> 这两条保留在报告里，是因为**测量工具错了要改工具，不能把错误数字当结论**。

### 0.5 一个被实测推翻的假设（重要）

任务描述里有一条假设：*「`sql.js`（1.15MB WASM）是否真的需要首屏加载？`codemirror` 与 Tiptap 是否可能只加载其一？」*

**Coverage 实测推翻了「codemirror 首屏 unusedBytes ≈ 0」这个推断**：

```
codemirror-DWuwBixc.js   总 958.8KB   已用 588.7KB   未用 370.1KB   未用率 38.6%
```

即 **codemirror 首屏已被执行 61.4%**，**不能整块懒加载**。
如果按原假设给出「543.8KB 全可延后」的建议，团队会花一个迭代做懒加载、收效甚微、还引入白屏闪烁。
正确方向见 §2.4。

（`sql.js` 未出现在任何首屏资源的 Coverage 结果里，说明它当前**不在首屏加载路径**上 —— 这条假设不成立，无需优化。）

### 1.2 关键结论：生产慢在哪一段

**三个事实**：

1. **shellMs 三轮高度一致**：828 / 844 / 819ms（第 2 轮的 201ms 是资源数只有 55 个的缓存命中场景，非正常冷启动）
2. **本地 shellMs 172ms，生产 823ms，差 651ms**
3. **首屏要下载的 JS/CSS 是 599.8KB**（§2.2）

> ⚠️ **重要归因更正**：我最初怀疑「生产 FCP 波动来自服务器资源竞争」（该机器总内存仅 3.6GB，同时跑 MySQL + 宝塔 + 另一 Node 项目）。
> 但 shellMs 三轮 819/828/844 的**高度稳定性**否证了这个猜测 —— 资源竞争会导致随机抖动，而这里是非常稳定地慢。
> **结论：生产首屏慢的主因是「网络传输 599.8KB」，不是服务器性能。** 优化方向应是减字节，不是加机器。

### 2.4 关于「codemirror 能否延后加载」的正确结论

**不能整块延后**，因为首屏已执行 61.4%。
可能的收益来自**拆分 CodeMirror 的按需子模块**：

| 候选 | 依据 | 预估收益 |
|---|---|---|
| `@codemirror/language-data`（上百种语言语法） | 只有源码/对照模式会高亮非 Markdown 语言 | 未测（需精确定位子模块体积） |
| `@codemirror/search` / 非首屏扩展 | 搜索面板按需打开 | 未测 |
| 拆出 CodeMirror 与 Tiptap 的**共享基础设施** | 两者共用选区/命令系统，这部分已用 588.7KB | 不可拆（是必需品） |

**结论**：这是一条**中等成本、收益待验证**的改造。不应作为 P0，且**改造前必须先做子模块级 Coverage**（本报告未做到这一粒度，如实标注未覆盖）。

### 2.5 🔴 最高价值发现：**100% 静态资源不可缓存**

生产所有资源（含带内容哈希的 JS/CSS）都返回：

```
Cache-Control: no-cache, no-store, must-revalidate
Pragma: no-cache
```

按资源类型统计（来自 15:49 那次抓取的 113 个响应）：

| 类型 | 数量 | 带 no-store/no-cache |
|---|---|---|
| document | 1 | **1（100%）** |
| script | 11 | **11（100%）** |
| stylesheet | 6 | **6（100%）** |
| fetch | 96 | 96（100%） |

**为什么这是问题**：
`codemirror-DWuwBixc.js` 这类文件名带内容哈希（`DWuwBixc`），内容变化才换名。这类资源**本应 `Cache-Control: public, max-age=31536000, immutable`**。
现在设成 `no-store`，意味着**用户每次访问都要重新下载 599.8KB** —— 二次访问和首次一样慢。

**收益预估**（保守）：
- 二次访问静态资源传输从 **599.8KB → 0KB**（304 命中）
- 按生产 shellMs 823ms 中 651ms 来自传输估算，**二次访问首屏可降至 200ms 量级**
- 对弱网用户收益更大（Slow 3G 下 599.8KB 要 ~10s，缓存命中后 < 1s）

**根因（已由 Lead 补查到确切位置）**：

问题在 **nginx 配置**，不是应用层。`/www/server/panel/vhost/nginx/node_neomd.conf:67-76`：

```nginx
location / {
    proxy_pass http://127.0.0.1:3200;
    proxy_cache off;
    # 入口 HTML 不缓存，避免发版后仍指向旧资源
    proxy_hide_header Cache-Control;                                    # ← 抹掉上游的
    add_header Cache-Control "no-cache, no-store, must-revalidate" always;   # ← 强制覆盖
    add_header Pragma "no-cache" always;
    ...
}
# 全文只有这一个 location /（另有 .git/.env 安全拦截块）
# 没有给 /assets/ 单独配置 → 带 hash 的 assets 也吃到 no-store
```

**应用层其实是对的**：`services/api/src/server.js:234` 确实有 `cacheControl: true`，
但被 `proxy_hide_header Cache-Control` 抹掉，再被 `add_header ... always` 强制覆盖。

**这是一处「注释与实现不符」**：注释写「**入口 HTML** 不缓存」，但 `location /` 的作用域是**整个站点**，把带内容哈希的 assets 一起设成了不缓存。

**修复方向**：新增 `location /assets/`（长缓存 + immutable），保留 `location = /index.html`（不缓存），从 `location /` 移除全局 no-store。

> 归因说明：这个问题由我（QA 审计）在 §2.5 通过响应头分析发现并量化收益；
> **具体 nginx 配置行号由 Lead 补查**，两者合并成完整结论。

### 2.6 HTML 未开 gzip

```
生产首页：Content-Length: 603B, Content-Encoding: (none)
```

603 字节虽小，但暴露 **nginx 的 `gzip_types` 未覆盖 `text/html`**。
一行配置（`gzip_types ... text/html`）零成本修复，且对**所有页面生效**（含分享页 `/p/*`）。

## 3. 运行时性能（本地）

### 3.1 长会话（输入 1000 字 + 插 50 块 + 滚到底）

### 3.3 多标签（20 个）

| 指标 | 值 |

### 4.4 🔴 弱网下「11 秒白屏」—— 最贴近用户痛点的证据

我用 500ms 间隔连续采样界面状态（`tools/audit-perf-06-weak-ux.mjs`），把「慢」还原成用户的真实体验：

**场景 1：冷启动（Slow 3G，400ms 延迟 / 62.5KB/s）**

| 时刻 | 外壳 DOM | 编辑器 | 加载提示 | 界面可见文本 |
|---|---|---|---|---|
| 507ms | 0 | 0 | **无** | **（空字符串）** |
| 2022ms | 0 | 0 | **无** | **（空字符串）** |
| 5044ms | 0 | 0 | **无** | **（空字符串）** |
| 8046ms | 0 | 0 | **无** | **（空字符串）** |
| 10064ms | 0 | 0 | **无** | **（空字符串）** |
| **11107ms** | **1** | 0 | spinner 出现 | 「正在打开本地仓库…」 |
| 12080ms | 1 | 0 | 无 | 「还没有打开任何文档」 |

**🔴 关键事实：从页面开始加载到第 11.1 秒，浏览器里是纯白屏 —— 没有任何文字、没有 spinner、没有骨架屏。**

这不是「加载慢」的体感问题，而是**用户会以为网站挂了**。8 秒是用户耐心阈值（Nielsen 的响应时间阈值：>10s 用户会离开），而这里 **11.1 秒纯白**。

**场景 2：点击「新建文档」→ 编辑器可用**

| 情形 | 编辑器出现耗时 | 有 loading 提示 |
|---|---|---|
| 外壳已加载完、chunk 已在缓存 | **508ms** ✅ | 不需要 |
| 首次打开（chunk 未加载，需下 700KB+） | **60 秒内未出现** ❌ | **无任何提示** |

**为什么两次差这么多（必须说清，否则会误导）**：
- 场景 2 的 508ms 是在**同一 context 内**、外壳加载后立即点击 —— 此时编辑器 chunk 已随首屏一起请求过，命中内存缓存
- 而 §4.3 的「editable=-1（超时）」是**首次**点击，需要现场下载 `editor`(384.6KB) + `EditorPage`(332.8KB)
- **两种情形都是真实用户会遇到的**：首次访问的用户属于后者

**所以准确的结论是**：
1. **首屏 11.1 秒纯白屏**（无任何反馈）← 最严重
2. **首次打开发文档时，编辑器 chunk 还要再下 700KB+，期间同样零反馈** ← 次严重

**收益预估**：
- 加一个「正在加载」骨架屏：**0 字节传输成本**，仅改 UI
- 配合 §2.5 的缓存修复：二次访问全部资源命中缓存，**白屏从 11.1s 降至 <1s**

### 4.5 并发 20 请求

| 目标 | 探测接口 | 串行中位 | 并发20 中位 | p95 | max | 墙钟 | 429 | 退化 |
|---|---|---|---|---|---|---|---|---|
| 生产 | `health`（无鉴权） | 28.4ms | 48.2ms | 57.6ms | 57.6ms | 62ms | 0 | **1.70x** |
| 生产 | `vaults`（有鉴权） | 17.7ms | 25.4ms | 32.6ms | 32.6ms | 34ms | 0 | **1.44x** |
| 本地 | `health` | 29.1ms | 14.6ms | 25.7ms | 25.7ms | 26ms | 0 | 0.50x |
| 本地 | `vaults` | 29.5ms | 15.2ms | 26.9ms | 26.9ms | 29ms | 0 | 0.52x |

**读法**：
- 生产并发 20 时退化 **1.44~1.70x**，绝对耗时仍在 **48ms 以内**，**可接受**
- 墙钟 62ms 处理完 20 个请求 → 吞吐约 **320 req/s**（单进程）
- **0 个 429**，说明只读接口没撞限流
- 本地「退化 0.5x」是因为串行测量含首次连接开销，并发时连接复用反而更快 —— 不是本地更快

**结论**：只读接口并发无瓶颈。未测**写接口并发**（受 20 次/分钟限流约束，无法安全压测），如实标注未覆盖。

### 5.3 EXPLAIN —— **未能执行（如实标注：权限不足 + 连接方式限制）**

**结论：未执行数据库 EXPLAIN。**

**两条具体原因**（不编造数据）：

1. **权限不足**：本审计以 `admin`（应用层管理员）身份通过 HTTP API 访问，**没有数据库账号凭据**。
   `services/api/.env` 里虽有 `DB_HOST` / `DB_NAME` / `DB_USER` / `DB_PASSWORD`，但
   - 读取并使用生产库凭据超出「只读审计」的授权边界；
   - 脚本刻意只读取 host/db 名用于确认连接目标，**不打印也不使用凭据**（见 `05-backend.mjs` 的 `tryExplain()`）。

2. **连接方式限制**：生产库 `tx.zhengl.vip` 仅对应用服务器开放，本机（审计环境）**无直连网络可达性**。

**替代方案（已做）**：
- **N+1 耗时比检测**（§5.2）：全部接口耗时比 ≤1.59，`admin/audit` 体积涨 4.72x 而耗时只涨 1.02x → 间接证明是批量查询
- **SQL 静态审计**：扫描 `admin.js` / `vaults.js` / `storage.js` / `plugins.js` 的 SELECT 语句，检查 `WHERE` / `LIMIT` / `JOIN` 与多表 FROM

**替代方案的局限（必须说清）**：
- 能排除「全表扫描级别的慢查询」（因为耗时与条目数不呈线性）
- **不能排除**「有索引但索引选择性差」的情况 —— 这必须真实 EXPLAIN 才能看到 `rows` / `type` / `Extra`

**复跑方式**（需 DB 权限）：
```sql
-- 在数据库侧执行（非应用层）
EXPLAIN SELECT * FROM users ORDER BY created_at DESC LIMIT 20;
EXPLAIN SELECT * FROM audit_logs ORDER BY created_at DESC LIMIT 20 OFFSET 0;
EXPLAIN SELECT * FROM user_vaults WHERE user_id = 1;
EXPLAIN SELECT * FROM plugins WHERE status = 'published' LIMIT 20;
-- 重点看 type 是否 ALL（全表）、rows 是否接近表总行数、Extra 是否 Using filesort/Using temporary
```

### 5.4 静态资源来源 —— ✅ nginx 直出（1.4.0 遗留风险已排除）

**这是任务描述里点名的风险点**：「静态资源是 nginx 直出还是 Node 转发（后者会吃 Node CPU）」

**结论：nginx 直出，风险不存在。** 证据链：

```
$ curl -I https://md.zhengl.vip/assets/codemirror-DWuwBixc.js
HTTP/1.1 200 OK
Server: nginx
etag: W/"2ceb5-1a18f522600"          ← nginx 格式 ETag（len-mtime hex）
Content-Encoding: gzip
Vary: Accept-Encoding
Last-Modified: Sat, 31 Oct 2026 00:18:08 GMT
Cache-Control: no-cache, no-store, must-revalidate   ← 问题在这里（见 §2.5）
```

**判定依据**：
1. `Server: nginx`（直出而非代理透传）
2. `ETag: W/"<hex>-<hex>"` 是 **nginx 的 `$content_length-$mtime_hex` 格式**；Node 的 `send` 库格式不同
3. `Content-Encoding: gzip` + `Vary: Accept-Encoding` 是 nginx `gzip` 模块行为
4. 对比：**本地 3200 的 `/assets/*` 返回 `503 WEB_NOT_DEPLOYED`** —— 说明本地 Node 确实注册了 `@fastify/static`（`server.js:229`），但**生产环境这个目录不存在**（`hasWebRoot=false`），所以生产是 nginx 直出

> 补充：`server.js` 的 `fastifyStatic` + SPA 回退（`app.get('/*')`，第 232-262 行）在生产环境下 `webRoot` 不存在时只走 SPA 回退，**不承担静态资源服务**。所以 Node CPU 没有被静态资源拖累。

**但 §2.5 的 `no-store` 问题需要排查**：响应带 `x-ratelimit-*` 头（说明经过了应用层中间件），这个 `no-store` 是**应用层加的还是 nginx 加的需要服务端定位**。

## 6. 最严重的 3 个瓶颈（按可量化收益排序）

### 🥇 P0：静态资源 `no-store` → 每次访问重下 599.8KB
