## 二、最重要的 8 项发现（摘要）

P0：
1. 生产服务无守护 —— 审计当天 502 六次，每次需人工拉起。
   根因链条清楚（退出后不自动拉起），但 SIGTERM 发送者未确证。
2. 生产管理员密码在公开仓库 47 个已跟踪文件里。
3. MySQL 3306 公网可建连 + 防火墙未启用（已实测公网侧可连）。
4. 仓库停用可被绕过（2 处漏网点：presignSchema 与 readRawBody 都丢了
   vaultId，导致 resolveScope 落 legacy 分支跳过 assertVaultUsable）。
   影响范围已核实：官方客户端走 header 不受影响，但注释声称支持 body
   与 multipart，属「无人使用但一旦使用就静默失效」的鉴权后门。
5. 新设备登录把云端统计清零（用户会以为数据全丢）。
   根本原因：数据库 28 张表里没有 documents 表，doc_count 是纯客户端上报，
   服务端既不能校验也不能重算 —— 属架构级缺陷，不是改一句 SQL 能解决。

P1：
6. 删除文档后云端对象永久残留（DELETE /api/storage/object 端点存在但全仓
   0 处调用）。用户以为删了，云端 .md 全文还在，涉隐私合规。
7. 插件下架无二次确认（已实证：误点一次让线上插件从市场消失）。
8. 数据核心 2715 行零测试（vault/registry/sync-engine/markdown-bridge）。

## 三、投入产出比最高的优化

静态资源 100% 不可缓存。已定位到 nginx 第 67-76 行：
`location /` 里的 `add_header Cache-Control "no-store"` 全站生效，
连带内容哈希的 assets 也不缓存。注释写的是「入口 HTML 不缓存」，
但作用域是整个站点 —— 注释与实现不符。
改 6 行配置：二次访问传输 599.8KB → 0，首屏 823ms → 约 200ms。

## 四、被实测推翻的三个假设（记录下来避免团队白干）

1. codemirror 543.8KB 并非「首屏 100% 可延后」—— Coverage 实测已执行
   588.7KB（61.4%），正确方向是拆按需子模块而非整块懒加载。
2. 生产 FCP 波动不是服务器资源竞争 —— shellMs 三轮 819/828/844 高度稳定，
   主因是传输 599.8KB。
3. @fastify/static 路径穿越实测未可利用（返回 200 但是 SPA index.html，
   未泄露任何文件）→ 从 P1 降为 P2。
   教训：「版本在 advisory 区间」≠「漏洞可利用」。

`tools/.env.example`（凭据只从 AUDIT_PASS 环境变量读）。

清理过程中靠 `node --check` + 自动回滚抓住两个自伤：
- 清理脚本第一版把密码写在正则里，自己成了新泄露点（改用字符码拼装）
- helper 被插到 shebang 之前导致 SyntaxError（已修正插入逻辑）

注意：清理代码只是次要措施，真正的修复是轮换密码。
清理解决「新代码不再犯」，轮换解决「已泄露的那份失效」，两者不可互替。
