## 缺陷1：编辑器行距过大

### 根因（先排除误判）
实测 `getComputedStyle`：`.wysiwyg__host.nm-content` / `.ProseMirror.nm-content` / `p`
三层的 computed `lineHeight` 全部是 **28px = 16px × 1.75**，
**不存在「两层 line-height 相乘」**（CSS 无单位 line-height 是直接覆盖，不是相乘）。

真实根因是两层同向放大：
1. 默认 `line-height: 1.75` 偏松 —— 28px 行盒里 16px 字形只占 20px 盒子，
   上下各 4px half-leading；
2. `.nm-content p { margin: 0.85em 0 }`（13.6px）叠在行盒之上。

两者相加后，相邻两段的**字形间净空白** = 13.6 + 4 + 4 = **21.6px = 1.35em**，
比一整个行盒还空 —— 这就是用户看到的「行距过大、段落之间更空」。

### 修复前后实测（Playwright，浅色 daylight / 深色 midnight 数值相同）

| 指标 | 修复前 | 修复后 | QA 断言 |
|---|---|---|---|
| A1 `lineHeight/fontSize` | 1.75（28px） | **1.6（25.6px）** | ∈[1.4,1.85] ✓ |
| A2 是否 line-height 叠加 | 否（28px = 16×1.75） | 否（25.6px = 16×1.6） | ✓ |
| A3 相邻非空段落空白（默认排版） | 21.59px / **1.35em** | 15.19px / **0.949em** | ∈[0.5,2.0]em ✓ |
| A3 段间夹 1 个显式空行 | 55.18px / **3.449em** | 31.19px / **1.949em** | ∈[0.5,2.0]em ✓ |
| 空段落高度（=空行视觉高度） | 28px 行盒 + 上下 margin 27.2px | **25.59px（1.6em），margin 0** | 一个空行 = 一个行盒 ✓ |
| 段落 margin | 13.6px（0.85em） | **9.6px（0.6em）** | — |

## 缺陷3：左右分屏右侧颜色不对

### 根因（两条独立成因，都要修）
1. **对照模式**（`CompareView.vue`）：右侧 `.compare__preview` 完全没有上纸色，
   透明 → 透出祖先 `.shell__main` 的 `background: var(--bg-elevated)`。
   浅色主题下 `--bg-elevated` 恰好也是白色，所以看不出来；
   一旦切到「chrome 色 ≠ 纸张色」的主题就露馅。
   同时 `--content-font-size` / `--content-line-height` 两个 prop **只传给了左侧** SourceEditor，
   右侧预览完全没绑 → 调字号行高时两栏对不上。
2. **左右分屏**（`EditorPage.vue` 样式块）：`.shell__splitpane` 写死 `background: var(--bg)`
   —— `--bg` 是**界面外壳色**（`--chrome-bg`），而左侧主栏透出的是纸张色 `--bg-elevated`。
   两者在浅色下接近（#ffffff vs #f2f4f7），深色下差异明显（#14171c vs #1b1f26）。

另外全仓**不存在** `--bg-paper` 变量（计算值为空串），所以修复用的是 `--content-bg`。

### 修复前后实测计算色值（Playwright）

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 浅色·对照模式 右栏背景 | `rgba(0,0,0,0)`（透明，透出 #ffffff） | **`rgb(255,255,255)`**（由自身 `.compare__body--preview` 绘制） |
| 浅色·对照模式 右栏文字 | `rgb(31,35,41)` | `rgb(31,35,41)`（同为 `--content-fg`） |
| 深色·对照模式 右栏背景 | `rgba(0,0,0,0)`（透明，透出 #14171c） | **`rgb(20,23,28)`**（由自身绘制） |
| 深色·对照模式 右栏文字 | `rgb(229,231,235)` | `rgb(229,231,235)` |
| 浅色·左右分屏 左栏 / 右栏 | 左 `rgb(255,255,255)` / 右 **`rgb(242,244,247)`** ❌ | 左 `rgb(255,255,255)` / 右 **`rgb(255,255,255)`** ✓ |
| 深色·左右分屏 左栏 / 右栏 | 左 `rgb(20,23,28)` / 右 **`rgb(27,31,38)`** ❌ | 左 `rgb(20,23,28)` / 右 **`rgb(20,23,28)`** ✓ |

修复后左右两栏背景与文字色**完全一致**，且都来自同一组变量（`--content-bg` / `--content-fg`）。

## 缺陷4：保存后空换行丢失

### 三层根因
1. **`markdownToHtml` 丢空行信息**：markdown-it 把连续空行当块分隔符直接丢弃。
   实测 `markdownToHtml('A\n\n\nB')` === `"<p>A</p>\n<p>B</p>"` —— **不产生空 `<p>`**，
   空行在进 HTML 那一刻就没了。（注：QA 观测到的「空 `<p>`」实际来自
   TipTap 里用户按回车产生的空段落节点，以及旧 `htmlToMarkdown` 的丢弃逻辑，不是加载链路。）
2. **`htmlToMarkdown` 丢空段落 + 丢文末换行**：`if (s) parts.push(s)` 把空段落整体丢弃；
   收尾 `.trim()` 吃掉文末换行 → 每次保存 git 都报 `\ No newline at end of file`。
3. **代码块内空行被压缩**：对整串 markdown 跑全局 `\n{3,}` 折叠，把围栏内空行一起吃了
   （`a\n\n\nb` → `a\n\nb`，这是数据损坏）。

### 修复方案：空行有可逆载体，数量关系双向互逆
```
原文 N 个连续空行  ⇄  渲染 (N-1) 个 <p class="nm-blank">  ⇄  回写 2+(N-1) 个换行
校验：N=1 → 2 换行（标准段落分隔）✓   N=2 → 3 换行 ✓   N=4 → 5 换行 ✓
```
- N=1 不产生空段落（否则每个段落之间都会多一行）；
- 围栏代码块内**不做任何空行统计**，逐字保留；
- 文末换行个数以原文件惯例为准（原 0 个就保持 0 个，原 N 个就保 N 个）；
- 用户按回车产生的空段落（带或不带 class）都回写成空行。

### 修复前后（`node tools/re121-blankline.mjs`）

| 用例 | 修复前 | 修复后 |
|---|---|---|
| 段间 2 空行 `A\n\n\nB` | `A\n\nB` ❌ | `A\n\n\nB` ✓ |
| 段间 3 空行 | `A\n\nB` ❌ | `A\n\n\n\nB` ✓ |
| 文末 3 空行 | `A`（全丢）❌ | `A\n\n\n\n` ✓ |
| 代码块内 3 空行 | `a\n\nb` ❌ | `a\n\n\nb` ✓ |
| 硬换行（行尾两空格） | 升级成段落分隔 ❌ | 原样保留 ✓ |
| 空段落（TipTap 回车） | 整体丢弃 ❌ | `A\n\n\nB` ✓ |
| **汇总** | **20 项中多项失败** | **20/20 PASS** |

修复前该脚本退出码 1（有失败项），修复后退出码 0。

## 关于「空 <p>」与 55.19px 的口径澄清

- `A\n\nB`（不含空段落）修复前实测 **21.59px / 1.35em**；
- `A\n\n\nB` 在 WYSIWYG 里被敲成「A / 空段落 / B」时修复前实测 **55.18px / 3.449em**。
- 两者都起因于「行高偏松 + 段落 margin」，但 55.18 那份额外的 28px 是**空段落自己占的一个行盒**，
  不是加载链路凭空生成的。修复后两者分别降到 15.19px（0.949em）和 31.19px（1.949em）。

## 导出链路配套（`exporters.ts`）

`markdownToHtml` 现在会产出 `<p class="nm-blank">`，而导出用的是自己一份 BASE_CSS
（不是 `content.css`），必须同步，否则「修了编辑器、坏了导出」。

实测（真实 Chromium 排版 `docs/shots-121/re121-export-blankline.png`）：
- `body` 行高 `25.6px`（16 × 1.6）；
- 空段落高度 **25.59px ≈ 一个行盒 25.6px**，`marginTop/marginBottom = 0px`，`minHeight = 25.6px`；
- 普通段落 margin `9.6px`（0.6em），与编辑器一致。

## 遗留风险

1. **导出侧的相邻 margin 未完全对齐**：编辑器里空段落会导致相邻段落 margin 清零
   （靠 `:has()` 相邻选择器），导出 BASE_CSS 只清了空段落自身的 margin，
   因此导出里「1 个显式空行」的段间距是 44.78px，编辑器里是 31.19px。
   影响：导出文件里空行略显宽松，不影响数据。如需完全对齐，需在 BASE_CSS 再加两条相邻选择器规则。
2. **`p:has(> br.ProseMirror-trailingBreak)` 依赖 TipTap 内部类名**。若将来升级
   TipTap 改了 trailing break 的 class，空段落的 margin 归零会失效（视觉变松，数据不受影响）。
   `p:empty` 与 `p.nm-blank` 两条兜底仍在。
3. **文末换行策略**采用「原文件有 N 个就保 N 个」。若用户从别的工具导入的文件尾部无换行，
   保存后仍无换行（这是有意的保真行为，但可能与「统一以换行结尾」的团队约定冲突）。
